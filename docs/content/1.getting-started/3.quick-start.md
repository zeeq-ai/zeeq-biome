We'll start with a code-review app so each choice has a concrete purpose: `Organization` and `User` form the seed, then `CodeRepository` → `PullRequestRecord` → `CodeReviewRecord` → `ActiveCodeReviewLock`. The entities are plain classes, trimmed here to the properties that matter. Entities and parents must be **reference types**.

## 1. A seed and a `TestBiome` entry point

Most tests in this app need an owner and an organization. Keeping them in a **seed** gives each scenario a known starting point. We'll wrap `Biome.Start` in `TestBiome` so individual tests do not have to repeat that setup.

```csharp [TestBiome.cs] {25-27,36}
using Zeeq.Biome;

public sealed record ZeeqSeed(User Owner, Organization Organization)
{
    public static ZeeqSeed Generate()
    {
        var owner = new User
        {
            Id = $"user_{Guid.CreateVersion7():N}",
            DisplayName = "Owner",
        };
        var organization = new Organization
        {
            Id = $"org_{Guid.CreateVersion7():N}",
            DisplayName = "Test Organization",
            CreatedByUserId = owner.Id,
        };
        return new(owner, organization);
    }
}

public static partial class TestBiome
{
    private static readonly BiomeOptions<ZeeqSeed> Options =
        new BiomeOptions<ZeeqSeed>().SeedEntities(seed =>
            [seed.Owner, seed.Organization]
        ); // saved first, in this order

    public static BiomeBuilder<ZeeqSeed, ZeeqSeed> Start(
        out ZeeqSeed seed,
        IBiomeStore? store = null,
        TimeProvider? time = null
    )
    {
        seed = ZeeqSeed.Generate();
        return Biome.Start(seed, Options, store, time);
    }
}
```

::note
Options are shared by every test. They **freeze on the first `Start`**, and changing them afterwards throws. Each `Start` creates a new session, so parallel tests are safe.
::

## 2. A blueprint

A repository needs an ID, an organization, and a creation time even when the test is about something else. Put those routine choices in a **blueprint**. Its factory receives a context (`ctx`) with the seed, clock, and ID generation.

```csharp [Blueprints.cs] {7-8,11}
public static partial class Blueprints
{
    public static readonly Blueprint<ZeeqSeed, CodeRepository> Repository =
        Blueprint.For<ZeeqSeed, CodeRepository>(ctx =>
            new()
            {
                Id = ctx.NewId("repo"), // "repo_<uuidv7>"
                OrganizationId = ctx.Seed.Organization.Id,
                OwnerQualifiedName = "zeeq-ai/example",
                Enabled = true,
                CreatedAtUtc = ctx.Now, // never DateTimeOffset.UtcNow
            }
        );
}
```

## 3. Your first test

With those defaults in place, the test can ask for a repository and check its relationship to the seed. There is no need to repeat the values the blueprint already supplies.

::code-group

```csharp [With Biome] {8}
public sealed class CodeRepositoryTests
{
    [Test]
    public async Task Repository_belongs_to_seed_organization()
    {
        await TestBiome
            .Start(out var seed)
            .AddOne(Blueprints.Repository, out var repo)
            .BuildAsync();

        await Assert.That(repo.OrganizationId).IsEqualTo(seed.Organization.Id);
    }
}
```

::code-collapse{label="Without Biome" name="setup"}
```csharp
public sealed class CodeRepositoryTests
{
    [Test]
    public async Task Repository_belongs_to_seed_organization()
    {
        var seed = ZeeqSeed.Generate();
        var now = DateTimeOffset.UtcNow;
        var repo = new CodeRepository
        {
            Id = $"repo_{Guid.CreateVersion7():N}",
            OrganizationId = seed.Organization.Id,
            OwnerQualifiedName = "zeeq-ai/example",
            Enabled = true,
            CreatedAtUtc = new DateTimeOffset(
                now.Ticks - now.Ticks % 10,
                TimeSpan.Zero
            ),
        };
        _db.AddRange(seed.Owner, seed.Organization, repo);
        await _db.SaveChangesAsync();

        await Assert.That(repo.OrganizationId).IsEqualTo(seed.Organization.Id);
    }
}
```
::

::

`AddOne` builds the entity **immediately**, so `repo` exists as soon as it returns. `BuildAsync` then saves everything once.

|Shape|Creates|`out`|
|---|---|---|
|`AddOne(bp, out var x)`|1 default|`T`|
|`AddOne(bp, out var x, x => …)`|1 customized|`T`|
|`Add(bp, out var xs)`|1 default|`T[]`|
|`Add(bp, out var xs, 3)`|3 defaults|`T[]`|
|`Add(bp, out var xs, x => …, x => …)`|one per customizer|`T[]`|

::caution
Every Add takes an `out`. Write `out _` when the test doesn't need the value. Calling `BuildAsync` a second time throws.
::

## 4. Customize only what the test is about

When the behavior depends on a particular value, set that value at the call site. This keeps the reason for the scenario next to the test that needs it.

```csharp [CodeRepositoryTests.cs] {3,7-9}
await TestBiome
    .Start(out _)
    .AddOne(Blueprints.Repository, out var disabled, r => r.Enabled = false)
    .Add(
        Blueprints.Repository,
        out var pair,
        r => r.OwnerQualifiedName = "zeeq-ai/api",
        r => r.OwnerQualifiedName = "zeeq-ai/web"
    )
    .BuildAsync();
```

A comma makes **a new entity**. `+` stacks **traits** (named `Action<T>` values) on the same entity:

```csharp [Traits.cs] {10,12}
public static class Repositories
{
    public static readonly Action<CodeRepository> Disabled = r => r.Enabled = false;
    public static readonly Action<CodeRepository> Hidden =
        r => r.VisibleInLibraryPicker = false;
}

await TestBiome.Start(out _)
    .Add(Blueprints.Repository, out var repos,
        Repositories.Disabled,                        // repos[0]: disabled
        // repos[1]: disabled and hidden
        Repositories.Disabled + Repositories.Hidden)
    .BuildAsync();
```

## 5. Children: chain, branch, fan out

A pull request needs the repository it belongs to. Passing that repository into a **child blueprint** keeps the relationship explicit. For a relationship further up the chain, use `ctx.Ancestor<T>()`.

```csharp [Blueprints.cs] {10,13}
public static readonly ChildBlueprint<
    ZeeqSeed,
    PullRequestRecord,
    CodeReviewRecord
> Review = Blueprint.ChildOf<ZeeqSeed, PullRequestRecord, CodeReviewRecord>(
    (pr, ctx) =>
        new()
        {
            Id = ctx.NewId("review"),
            PullRequestRecordId = pr.Id, // typed parent
            OrganizationId = pr.OrganizationId,
            Status = CodeReviewStatus.Pending,
            RepositoryId = ctx.Ancestor<CodeRepository>().Id, // grandparent
            CreatedAtUtc = ctx.Now,
        }
);
```

**Every Add re-anchors to its own output**, so a chain reads top to bottom:

::code-group

```csharp [With Biome] {4-5}
await TestBiome
    .Start(out _)
    .AddOne(Blueprints.Repository, out var repo)
    .AddOne(Blueprints.PullRequest, out var pr) // parent: repo
    .AddOne(Blueprints.Review, out var review) // parent: pr
    .BuildAsync();
```

::code-collapse{label="Without Biome" name="setup"}
```csharp
var seed = ZeeqSeed.Generate();
var now = DateTimeOffset.UtcNow;
now = new DateTimeOffset(now.Ticks - now.Ticks % 10, TimeSpan.Zero);

var repo = new CodeRepository
{
    Id = $"repo_{Guid.CreateVersion7():N}",
    OrganizationId = seed.Organization.Id,
    OwnerQualifiedName = "zeeq-ai/example",
    Enabled = true,
    CreatedAtUtc = now,
};
var pr = new PullRequestRecord
{
    Id = $"pr_{Guid.CreateVersion7():N}",
    OrganizationId = repo.OrganizationId,
    RepositoryId = repo.Id,
    PullRequestNumber = 1,
    Title = "Pull request 1",
    Branch = "feature/1",
    State = PullRequestState.Open,
    CreatedAtUtc = now,
};
var review = new CodeReviewRecord
{
    Id = $"review_{Guid.CreateVersion7():N}",
    OrganizationId = pr.OrganizationId,
    PullRequestRecordId = pr.Id,
    RepositoryId = repo.Id,
    Status = CodeReviewStatus.Pending,
    CreatedAtUtc = now,
};
_db.AddRange(seed.Owner, seed.Organization, repo, pr, review);
await _db.SaveChangesAsync();
```
::

::

::note
A child Add **compiles only when the current anchor is its parent type**. Adding a `Review` straight after a repository is a compile error.
::

`.Under(x)` jumps back to an earlier output. **Fan-out is per parent**: each customizer runs once for every parent.

```csharp [FanOutTests.cs] {5}
await TestBiome
    .Start(out _)
    .Add(Blueprints.Repository, out var repos, 2)
    // 3 per repo → 6 PRs, ordered by parent
    .Add(Blueprints.PullRequest, out var prs, 3)
    .BuildAsync();
```

## 6. Sequences, then save

Numbering by position works for one Add, but restarts when you add more entities later. Declare a sequence so numbering continues across calls. Its state lives in each session, keeping tests independent:

```csharp [Blueprints.cs] {1-3,21}
public static readonly Sequence<int> PullRequestNumbers = Sequence
    .Of(1, n => n + 1)
    .Per<CodeRepository>(); // restarts per repository

public static readonly ChildBlueprint<
    ZeeqSeed,
    CodeRepository,
    PullRequestRecord
> PullRequest = Blueprint
    .ChildOf<ZeeqSeed, CodeRepository, PullRequestRecord>(
        (repo, ctx) =>
            new()
            {
                Id = ctx.NewId("pr"),
                OrganizationId = repo.OrganizationId,
                RepositoryId = repo.Id,
                State = PullRequestState.Open,
                CreatedAtUtc = ctx.Now,
            }
    )
    .Derive(pr => pr.PullRequestNumber, PullRequestNumbers)
    .Derive(pr => pr.Title, (pr, _) => $"Pull request {pr.PullRequestNumber}");
```

Finally, save with EF Core. Add a second `Start` overload that wraps `EfCoreStore`:

```csharp [TestBiome.cs] {7}
using Zeeq.Biome.EntityFrameworkCore;

public static BiomeBuilder<ZeeqSeed, ZeeqSeed> Start(
    DbContext db,
    out ZeeqSeed seed,
    TimeProvider? time = null
) => Start(out seed, db.AsBiomeStore(), time);
```

```csharp [CodeReviewTests.cs] {3}
await TestBiome
    .Start(_db, out var seed)
    .AddLockedReview(out var activeLock)
    .BuildAsync(); // AddRange in order, one SaveChangesAsync

_db.ChangeTracker.Clear(); // so the code under test reads rows from the database
```

::tip
`AddLockedReview` is a **scenario helper**: a named chain you write once. See [Scenario helpers and sugar](/guides/scenario-helpers-and-sugar). The four-line sugar methods are what keep chains short.
::
