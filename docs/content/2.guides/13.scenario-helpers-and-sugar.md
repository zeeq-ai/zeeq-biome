## The four sugar methods

Calling `AddOne` with a blueprint works, but repeating the blueprint name adds noise to every test. Four short extension methods let the chain use your domain's own names: singular and plural, each with and without customizers. Declare them in C# 14 `extension` blocks.

- **Root** types go on `extension<TAnchor>(BiomeBuilder<TSeed, TAnchor> b)`, so they are offered from any anchor.
- **Child** types go on `extension(BiomeBuilder<TSeed, TParent[]> b)`, so IntelliSense offers them only right after their parent.

::code-group

```csharp [Sugar (CodeReviews)] {4,27}
public static class CodeReviewSugar
{
    // Root type: offered from any anchor.
    extension<TAnchor>(BiomeBuilder<ZeeqSeed, TAnchor> b)
    {
        public BiomeBuilder<ZeeqSeed, CodeRepository[]> AddCodeRepository(
            out CodeRepository repo
        ) => b.AddOne(Blueprints.Repository, out repo);

        public BiomeBuilder<ZeeqSeed, CodeRepository[]> AddCodeRepository(
            out CodeRepository repo,
            Action<CodeRepository> customize
        ) => b.AddOne(Blueprints.Repository, out repo, customize);

        public BiomeBuilder<ZeeqSeed, CodeRepository[]> AddCodeRepositories(
            out CodeRepository[] repos,
            int count
        ) => b.Add(Blueprints.Repository, out repos, count);

        public BiomeBuilder<ZeeqSeed, CodeRepository[]> AddCodeRepositories(
            out CodeRepository[] repos,
            params Action<CodeRepository>[] customize
        ) => b.Add(Blueprints.Repository, out repos, customize);
    }

    // Child type: offered only when the anchor is CodeRepository[].
    extension(BiomeBuilder<ZeeqSeed, CodeRepository[]> b)
    {
        public BiomeBuilder<ZeeqSeed, PullRequestRecord[]> AddPullRequest(
            out PullRequestRecord pr
        ) => b.AddOne(Blueprints.PullRequest, out pr);

        public BiomeBuilder<ZeeqSeed, PullRequestRecord[]> AddPullRequest(
            out PullRequestRecord pr,
            Action<PullRequestRecord> customize
        ) => b.AddOne(Blueprints.PullRequest, out pr, customize);

        public BiomeBuilder<ZeeqSeed, PullRequestRecord[]> AddPullRequests(
            out PullRequestRecord[] prs,
            int count
        ) => b.Add(Blueprints.PullRequest, out prs, count);

        public BiomeBuilder<ZeeqSeed, PullRequestRecord[]> AddPullRequests(
            out PullRequestRecord[] prs,
            params Action<PullRequestRecord>[] customize
        ) => b.Add(Blueprints.PullRequest, out prs, customize);
    }
}
```

```csharp [Core API, no sugar] {3-8}
await TestBiome
    .Start(out _)
    .AddOne(Blueprints.Repository, out var repo)
    .AddOne(
        Blueprints.PullRequest,
        out var pr,
        p => p.State = PullRequestState.Closed
    )
    .BuildAsync();
```

::

With sugar, a chain names the **entities**, not the blueprints:

::code-group

```csharp [With sugar] {5}
await TestBiome
    .Start(_db, out var seed)
    .AddCodeRepository(out var repo)
    // the property under test
    .AddPullRequest(out var pr, p => p.State = PullRequestState.Closed)
    .BuildAsync();
```

```csharp [Core API] {4-8}
await TestBiome
    .Start(_db, out var seed)
    .AddOne(Blueprints.Repository, out var repo)
    .AddOne(
        Blueprints.PullRequest,
        out var pr,
        p => p.State = PullRequestState.Closed
    )
    .BuildAsync();
```

::

::note
Child sugar only appears **after its parent step** (the anchor type). If `AddPullRequest` is missing from IntelliSense, the anchor isn't a `CodeRepository[]`: add the parent first, or `.Under(parent)`.
::

### Sugar conventions

- Name methods `Add<Singular>` and `Add<Plural>` using the domain's own word (`AddPendingInvitation`, not `AddOrganizationMembership`).
- **Singular** methods return `T` through `out`. **Plural** methods return `T[]`. Both re-anchor to `T[]`.
- Sugar accepts `Action<T>` by default. For a one-off context-aware customizer, use the core `AddOne` / `Add` with the blueprint directly.
- Start with **four** per type. Add a [context overload](#context-overloads-when-a-test-needs-them) only for a type whose tests keep needing the clock or parent. Don't add overloads without `out`; callers write `out _`.
- Never create ancestors inside a child sugar method. Write a named scenario helper instead.

::warning
Don't mix `x => …` and `(x, ctx) => …` lambdas in one call. C# can't infer both. Without a context overload, `Action<T>` sugar can't take a two-parameter lambda, so use the core API for `ctx`.
::

### Context overloads: when a test needs them

Four methods cover most tests. When a type's tests repeatedly depend on the clock, such as "created five minutes ago", add one named context overload for that type instead of a context form for every method. The library's own `CodeReviews` tests do this for the repository:

```csharp [CodeReviews/Sugar.cs] {3}
public BiomeBuilder<CodeReviewSeed, CodeRepository[]> AddCodeRepository(
    out CodeRepository entity,
    Action<CodeRepository, BiomeContext<CodeReviewSeed>> customize
) => b.AddOne(Blueprints.Repository, out entity, customize);
```

```csharp [CodeReviews/CodeReviewTests.cs] {3}
.AddCodeRepository(
    out var second,
    (repo, ctx) => repo.CreatedAt = ctx.Ago(TimeSpan.FromMinutes(5))
)
```

C# picks the overload by the lambda's parameter count, so existing `r => …` calls still compile. A child overload takes `Action<T, ChildContext<TSeed, TParent>>`. Every lambda in one call must still use the same form.

## Scenario helpers

A lock test needs the repository, pull request, and review that lead to the lock, but usually asserts only on the lock itself. When that branch recurs, give it a **scenario helper**. This is an app-level chain declared on the seed anchor, returning the leaf while keeping all the construction steps visible in its definition:

```csharp [Sugar.cs] {2,7-10}
// Scenario helper: a whole default chain, offered from the seed only.
extension(BiomeBuilder<ZeeqSeed, ZeeqSeed> b)
{
    public BiomeBuilder<ZeeqSeed, ActiveCodeReviewLock[]> AddLockedReview(
        out ActiveCodeReviewLock activeLock
    ) =>
        b.AddCodeRepository(out _)
            .AddPullRequest(out _)
            .AddCodeReview(out _)
            .AddActiveLock(out activeLock);
}
```

A lock test now names only the lock:

::code-group

```csharp [With Biome] {1}
await TestBiome.Start(_db, out _).AddLockedReview(out var activeLock).BuildAsync();
```

::code-collapse{label="Without Biome" name="setup"}
```csharp
// Every test that needs a lock repeats the whole graph.
var repo = NewRepository(seed);
var pr = NewPullRequest(repo);
var review = NewCodeReview(pr);
var activeLock = NewActiveLock(review);
_db.AddRange(seed.Owner, seed.Organization, repo, pr, review, activeLock);
await _db.SaveChangesAsync();
```
::

::

::tip
A short call site should still be explainable. Keep the whole chain in the helper's definition so a reader can follow the rows it creates. Biome does not create missing ancestors automatically.
::

Scenario helpers can take parameters. The library's `Learning` domain passes a deadline through:

```csharp [Learning/Sugar.cs] {5,11}
extension(BiomeBuilder<LearningSeed, LearningSeed> b)
{
    public BiomeBuilder<LearningSeed, Submission[]> AddLateSubmission(
        out Submission leaf,
        DateTimeOffset dueAt
    ) =>
        b.AddSchool(out _)
            .AddCourse(out _)
            .AddSection(out _)
            .AddEnrollment(out _)
            .AddAssignment(out _, a => a.DueAt = dueAt)
            .AddSubmission(out leaf);
}
```

## Where to put things

```text [Layout]
Tests.Common/Biome/
  ZeeqSeed.cs             seed type + Generate()
  TestBiome.cs            options + Start overloads (no-DB, DbContext)
  CodeReviews/
    Blueprints.cs         sequences, blueprints, variants (one file: init order)
    Traits.cs             PullRequests.Closed, …
    Sugar.cs              four one-liners per type + scenario helpers
  Membership/ …
```
